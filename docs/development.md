# Development

## Repository layout

```
src/<feature>/devcontainer-feature.json   Feature metadata and options
src/<feature>/install.sh                  Install script (runs as root at build time)
src/<feature>/NOTES.md                    Hand-written notes appended to the generated README
test/<feature>/scenarios.json             Scenario tests (pinned versions, base images)
test/<feature>/*.sh                       Assertions run inside each scenario
.github/workflows/                        Validate, test and release pipelines
docs/                                     This documentation
```

Each feature’s `README.md` is generated from `devcontainer-feature.json` on release. Edit `NOTES.md` instead of the README. This `docs/` folder is hand-written and is not touched by the generator.

## Dev container

Open the repository in its dev container. It ships the `devcontainer` CLI (installed with `npm install -g @devcontainers/cli` on content update), Docker-in-Docker and the GitHub CLI.

## Testing

```bash
# Autogenerated tests for one feature against a base image
devcontainer features test --skip-scenarios -f bun -i ubuntu:latest .

# Scenario tests (pinned versions)
devcontainer features test -f bun --skip-autogenerated --skip-duplicated .
```

Scenarios are defined in `test/<feature>/scenarios.json`, and each scenario name matches a script of the same name in that folder (for example `test/node/pinned.sh`), which asserts what should be installed. `test/<feature>/test.sh` is the autogenerated test.

| Feature | Scenarios |
| :--- | :--- |
| `bun` | `1.0.0`, `1.2.0` |
| `deno` | `2.0.0`, `2.1.7` |
| `node` | `pinned`, `major`, `all`, `yarn-classic`, `none` |

When you add an option or change behavior, add or adjust a scenario and its assertions.

## Continuous integration

| Workflow | When | What it does |
| :--- | :--- | :--- |
| Validate devcontainer-feature.json files | Pull requests | Validates every `devcontainer-feature.json` against the spec schema |
| CI - Test Features | Pushes to `master`, pull requests, Mondays 06:00 UTC | Runs the autogenerated tests for each feature on `debian:latest`, `ubuntu:latest` and `mcr.microsoft.com/devcontainers/base:ubuntu`, and the scenario tests for each feature |
| Release dev container features & Generate Documentation | Pushes to `master` that touch `src/`, or manually | Publishes features and opens a PR with regenerated READMEs |

## Releasing

1. Bump `version` in the feature’s `devcontainer-feature.json`: patch for a fix, minor for a new option, major for a breaking change. The **Version bump** check fails a pull request that changes a feature (anything in `src/<feature>/` but its `README.md` and `NOTES.md`) without bumping it, since an unbumped change would never be published.
2. Merge to `master`.

The release workflow publishes only features whose version is not yet in GHCR, makes a GitHub Release for each version it published (`feature_<id>_<version>`, its notes the commits that changed the feature since its previous version), then opens a pull request with the regenerated per-feature READMEs. `.github/scripts/create-releases.sh` makes any release that's missing; with `DRY_RUN=1` it prints them instead. Merging that pull request triggers one more run, which finds nothing to publish.

The workflow uses the built-in `GITHUB_TOKEN`; no secrets are required. One-time setup: enable **Settings > Actions > General > Allow GitHub Actions to create and approve pull requests**, otherwise the docs pull request step fails. Pull requests opened this way do not trigger CI, which is fine for generated READMEs.

Changes that only touch `docs/` do not trigger a release.
